## 절대 하지 말 것

1. **조사 없이 글을 찍어내지 않는다.** 발행 속도는 하루 3편이 상한이며,
   발행 전 필수 조건을 못 채우면 미룬다. 편수를 채우려고 대충 쓰는 것이
   사흘에 98편과 같은 짓이다. 상세 규칙은 `CLAUDE.md` 1번.
2. **발행일(`date:`)을 조작하지 않는다.** 구글은 첫 크롤 날짜를 갖고 있어
   어긋나면 더 나쁜 신호가 된다. 대신 `updated` 를 정직하게 쓴다.
3. **보호자 노트에 확인되지 않은 경험을 쓰지 않는다.**
   `docs/caregiver-facts.md` 에 있는 것만. 지어낸 한 줄이 전체 신뢰를 깎는다.
4. **승인 전까지 `PUBLIC_ADS_ENABLED` 를 켜지 않는다.** 없어야 광고가 꺼진다.
5. **법령·제도는 반드시 팩트체크 절차를 거친다. 예외 없다.**
   6단계 절차는 `CLAUDE.md` 5번에 있다. 개인 블로그·언론 기사·AI 기억은
   출처가 아니다. 공식 출처끼리 엇갈리면 직접 열어 확인하고, 그래도 안 되면
   그 수치를 뺀다. **의심스러우면 쓰지 않는다.**
6. **특정 병원·시설 실명을 쓰지 않는다.**
7. **23:00~07:00 에는 푸시하지 않는다.** 푸시가 곧 배포이므로 푸시 시각이
   곧 게시 시각이다. 밤에 완성했으면 커밋만 하고 아침에 푸시한다.

## 2026-08-17 운영 사고 3건과 교훈

### ① 크론이 키체인을 못 열어 발행 3연속 실패

09/12/15시 전부 `could not read Username ... Device not configured`.
**cron 은 GUI 로그인 세션 밖에서 돌아 macOS 키체인에 접근하지 못한다.**
`env -i` 최소 환경에서도 키체인은 열리므로 환경변수가 아니라 **세션** 문제다.

→ **launchd 로 교체.** `~/Library/LaunchAgents/kr.noado.publish.plist`
사용자 Aqua 세션 안에서 실행되어 키체인이 열린다. 실측 검증 완료.
**crontab 에 블로그 항목을 다시 넣지 말 것.** 중복 등록되면 크론이
헛경보를 띄운다.

### ② 검증하다가 상한 가드를 뚫고 글이 하루 일찍 발행됨

`.publish-state` 를 `1999-01-01 0` 으로 덮어써 테스트했더니 스크립트가
설계대로 다음 글을 실제로 푸시했다. **스크립트 결함이 아니라 운영 실수.**

→ 두 가지를 고쳤다.
- **`--dry-run` 모드 추가.** 검증은 반드시 이걸로 한다.
- **상한을 git 사실에서 센다.** `origin/main@{오늘 00:00:00}` 부터 현재까지
  원격에 올라간 글 커밋 수. 상태 파일을 조작해도 뚫리지 않는다.

### ③ crontab 을 통째로 재작성해 타 프로젝트를 위협함

cron→launchd 전환 중 `crontab -l` 받아 통째로 재작성했다. 인스타 5줄이
살아남았는지 확인도 안 했다. 운 좋게 보존됐을 뿐이다. 게다가 오씨에게
통보하지 않아 다른 세션이 사고로 오인하고 복구 작업까지 했다.

→ **crontab 을 건드릴 때 지킬 것 (그룹 규칙 신설됨)**
1. 통째 재작성 금지
2. 적용 **전에** 타 프로젝트 줄 수를 세어 일치할 때만 적용
3. 오케스트레이터에게 **사전 통보**
4. 백업을 남긴다

**공통 교훈: 커밋 메시지에만 적는 것은 통보가 아니다.**
